## What `invariants_py` is

It is a Python research library for representing trajectories through quantities that do not depend on the arbitrary coordinate frame used to describe them. Its stated purpose is to:

* calculate invariant descriptors from trajectory data;
* reconstruct or generate trajectories from those descriptors;
* adapt trajectories while imposing endpoint or other geometric constraints.

For an ordinary spatial curve, its principal translational invariant variables are essentially:

[
u(s)=
\begin{bmatrix}
v(s)\
\kappa(s)\
\tau(s)
\end{bmatrix},
]

where (v) is traversal speed, (\kappa) is curvature, and (\tau) is torsion. The code explicitly integrates a moving Frenet–Serret-like frame using these three quantities.

It also handles orientation trajectories, rigid-body poses, moving frames, and constrained trajectory generation. Underneath, it uses CasADi to formulate and solve geometric optimal-control problems. Its declared dependencies include CasADi, SciPy, NumPy, Matplotlib, PyQt5, Pandas, and some robotics libraries.

The repository currently declares version `0.3.9`, classifies itself as alpha-stage research software, supports Python 3.8–3.12, and uses the MIT license.   It was still receiving commits as recently as May 6, 2026.

## Why it is interesting for the H-universe work

This is quite close to one part of what we have been discussing, but not to the entire physical system.

Its strongest potential uses are:

1. **Extracting a compact geometric state from a generated curve.**
   Instead of treating thousands of vertex coordinates as the fundamental description, a droplet centerline, filament, or material trajectory can be represented through evolving invariant quantities.

2. **Reconstructing geometry from invariant “instructions.”**
   A sequence of curvature and torsion values acts somewhat like a geometric program telling a moving frame how to propagate. That resembles your distinction between the underlying manifold laws and the rendered universe produced by those laws.

3. **Constrained trajectory generation.**
   You could prescribe initial and final positions, orientations, smoothness requirements, or invariant profiles and ask the optimizer to find a compatible trajectory.

4. **A model for making the solver more agile.**
   CasADi builds a symbolic computational graph and lets an optimizer handle the coupled constraints. This can replace a large amount of hand-written iterative adjustment code.

There is an especially relevant conceptual decomposition:

[
\text{invariant field}
\quad\longrightarrow\quad
\text{moving-frame dynamics}
\quad\longrightarrow\quad
\text{embedded trajectory}.
]

For the H-universe program, that could become:

[
\mathcal I(\lambda)
\quad\longrightarrow\quad
\dot F(\lambda)=F(\lambda),\Omega[\mathcal I(\lambda)]
\quad\longrightarrow\quad
X(\lambda),
]

where (\mathcal I) contains the local geometric “law variables,” (F) is the evolving frame, and (X) is the resulting embedded worldline, worldtube axis, boundary trajectory, or material history.

## Important limitation: it is presently a 3D robotics package

The implementation is built primarily around:

[
SO(3),\qquad SE(3),
]

three-dimensional rotation matrices and ordinary spatial trajectories. You can see that throughout the integrators: frames are (3\times3), positions are three-vectors, and Rodrigues’ rotation formula is used for spatial rotations.

It therefore does **not** immediately provide:

* four-dimensional Frenet-frame propagation;
* a Minkowski or Lorentzian metric;
* worldtube cross-sections;
* interacting filaments;
* fields on a deformable universe surface;
* topology change or droplet breakup;
* a physical action governing evolution;
* stress-energy or continuum mechanics.

For a regular curve in four-dimensional Euclidean space, the generalized Frenet system normally needs three curvature functions rather than the 3D pair (\kappa,\tau):

[
\kappa_1,\qquad \kappa_2,\qquad \kappa_3.
]

The moving frame becomes (4\times4), and its generator has the schematic form

[
\Omega =
\begin{pmatrix}
0 & \kappa_1 & 0 & 0\
-\kappa_1 & 0 & \kappa_2 & 0\
0 & -\kappa_2 & 0 & \kappa_3\
0 & 0 & -\kappa_3 & 0
\end{pmatrix}.
]

That is the direction in which its central machinery would have to be generalized for a strict 4D H(s)H implementation.

## It does not quite “generate a Lagrangian”

The phrase **geometric optimal control** can make this sound more physically dynamical than it is.

CasADi lets the developers define:

* state evolution equations;
* control variables;
* boundary constraints;
* an objective or cost functional.

That objective may look mathematically like an action,

[
J=\int L(x,\dot x,u),d\lambda,
]

but it is not automatically a physical Lagrangian. In this package, the function is primarily an optimization criterion used to recover or adapt trajectories. The physics would still have to come from us.

A good SAT/H-universe use would therefore be:

[
S_{\mathrm{physical}}[X,F,\mathcal I,\Phi]
]

defines the actual allowable evolution, while the package’s optimal-control architecture supplies the numerical transcription and solver structure. In other words, it offers a potentially useful **solver chassis**, not the H-universe engine itself.

# Primary scientific libraries

## NumPy 2.3.4 — the numerical substrate

NumPy is the most load-bearing library in the environment. It provides multidimensional arrays, vectorized arithmetic, shape operations, Fourier transforms, random simulation, statistics, and basic linear algebra. ([NumPy][1])

For H(s)H, it can represent structures such as:

```python
H.shape == (n_samples, 4)
```

for one sampled four-dimensional history,

```python
H.shape == (n_histories, n_samples, 4)
```

for an ensemble, or

```python
frame.shape == (n_samples, 4, 4)
```

for a moving four-frame along a history.

Practical SAT capabilities include:

* finite-difference estimates of (H'), (H''), (H'''), and higher derivatives;
* tangent normalization and arc-length reparameterization;
* metric contractions such as (v^\mu g_{\mu\nu}v^\nu);
* Gram matrices and frame orthogonalization;
* eigenvalues, eigenvectors, singular-value decompositions, and matrix inverses;
* numerical curvature and generalized-curvature estimators;
* phase arrays, winding counters, holonomy accumulators, and braid-state arrays;
* vectorized evaluation of constraints over an entire history;
* FFT-based detection of helical and superhelical frequencies;
* ensemble runs and perturbation tests.

A particularly useful NumPy operation for SAT is `einsum`, which lets you express contractions without writing slow Python loops:

```python
norm_sq = np.einsum("ni,ij,nj->n", tangent, metric, tangent)
```

NumPy does **not** understand that an array represents a tensor, metric, connection, worldtube, action, or physical law. It carries out the operations you specify. It also lacks native symbolic algebra, automatic differentiation, sophisticated optimization, general ODE/PDE solvers, and manifold-aware integration.


comes from the VTK–Matplotlib text-rendering bridge. It concerns a requested visual effect on mathematical text, not the underlying numerical calculation.

**SAT role:** quantitative diagnostics and publication figures.

---

## Plotly 6.8.0 — interactive reports and browser dashboards

Plotly produces interactive, publication-quality browser graphics, including scientific charts, 3D scatter and surface plots, animations, sliders, buttons, hover information, and notebook widgets. ([Plotly][6])

For SAT it is particularly useful for:

* interactive Global Run Summaries;
* hoverable residual and invariant traces;
* run-to-run comparison dashboards;
* parameter-space exploration;
* three-dimensional projected trajectories;
* animated parameter scans;
* HTML reports that can be opened without rerunning the solver;
* linked tables and charts;
* filtering runs by UUID, action reference, equation family, or status.

Plotly occupies the middle ground between Matplotlib and PyVista:

```text
Matplotlib → precise static diagnostics
Plotly     → shareable interactive data diagnostics
PyVista    → scientific 3D geometry and mesh interaction
```

Plotly’s 3D scene system is not intended to become your core mesh-evolution engine. Very large or frequently updated meshes will generally be more natural in PyVista/VTK.

**SAT role:** interactive analytical reporting.

---

## Trimesh 4.12.2 — geometry validation and surface auditing

Trimesh specializes in loading, manipulating, and analyzing triangular meshes, with particular attention to watertight surfaces. Its capabilities include mesh-format conversion, face adjacency, curvature-related quantities, cross-sections, mass properties, repair, connected components, ray queries, boolean operations, voxelization, proximity calculations, and watertightness checks. ([Trimesh][7])

For SAT, it is useful after a projected or constructed worldtube skin has been triangulated.

It can test or calculate:

* whether a surface is watertight;
* Euler characteristic;
* disconnected components;
* duplicate or degenerate geometry;
* inconsistent face winding;
* normals and local face orientation;
* holes and some repairable defects;
* volume and surface area;
* center of mass;
* inertia tensor and principal inertia directions;
* cross-sections;
* nearest-surface points and signed distances;
* ray intersections;
* unions, intersections, and differences;
* export to GLB, STL, OBJ, PLY, and related formats.

This makes it ideal for questions such as:

```text
Did the generated tube unexpectedly split?
Did the projection create a self-crossing or nonmanifold surface?
Did remeshing change the Euler characteristic?
Is this object closed?
Are normals consistently oriented?
How much volume or area drift occurred?
```

However, Trimesh audits the **three-dimensional triangulated realization**. Its Euler number is not automatically the topology of the full 4D H(s)H object. Nor does it solve continuum mechanics, field equations, or general high-dimensional topology.

**SAT role:** projected-worldtube mesh auditor and exporter.

# Standard-library capabilities

These modules support architecture and reproducibility rather than mathematical physics.

`os` handles paths, folders, environment variables, file discovery, and process-level interaction. For new code, `pathlib` is often easier to audit than long chains of `os.path` calls.

`re` supports notation parsing, log extraction, filename interpretation, and validation of structured identifiers. It may be useful for your six-slot notation, but regex should not become the parser for a deeply nested mathematical language; a proper tokenization stage becomes safer once the grammar grows.

`random` supplies scalar pseudorandom choices. For numerical ensembles and reproducible vectorized perturbations, prefer NumPy’s explicit generator:

```python
rng = np.random.default_rng(seed)
```

`uuid` is excellent for run identity, object identity, conversation IDs, action references, and preventing accidental filename collision.

`datetime` supplies timestamps and durations. Store machine-readable timestamps in a timezone-aware ISO format rather than relying solely on human-formatted dates.

`sys` exposes command-line arguments, Python version details, module paths, standard input/output, and controlled program exits.

Several additional standard modules would fit naturally into the existing architecture without installing anything:

```text
pathlib      typed filesystem paths
json         structured metadata
hashlib      hashes for equations, inputs, and outputs
logging      persistent diagnostic logs
dataclasses  explicit state/configuration objects
enum         controlled state and mode vocabularies
argparse     basic CLI, although Cyclopts is stronger
subprocess   controlled external-tool invocation
traceback    exception capture
```

# Support and utility packages

## Rich and rich-rst

Rich supports formatted terminal tables, panels, progress indicators, live displays, syntax display, logging, trees, prompts, and enhanced tracebacks. ([Rich Documentation][8])

For SAT this can provide:

* a live iteration dashboard;
* color-coded constraint violations;
* nested object hierarchies;
* run-summary tables;
* readable exception reports;
* progress bars for sweeps;
* clear separation of geometry, physics, projection, and rendering stages.

`rich-rst` is principally a rendering bridge for reStructuredText content. It is a presentation dependency, not a scientific capability.

## Scooby

Scooby is largely present to support environment reporting. PyVista’s `Report` facility records operating-system, CPU, memory, GPU, Python, PyVista, VTK, NumPy, Scooby, Pooch, Matplotlib, and related package information. ([PyVista][9])

That is more important for SAT than it may appear. Every authoritative run can include an environment snapshot, making rendering or numerical differences easier to trace.

For example:

```python
import pyvista as pv

report = pv.Report()
print(report)
```

## Pooch

Pooch downloads scientific data only when required, caches it locally, verifies file hashes, supports data repositories and DOIs, and can automatically unpack compressed files. ([Fatiando][10])

Potential SAT uses include:

* retrieving standard comparison datasets;
* pinning observational input files by checksum;
* ensuring every machine uses the same reference data;
* caching large example meshes;
* associating a run with an exact immutable dataset version.

It is much safer for reference datasets than scattering ad hoc `requests.get(...)` calls throughout the code.

## Cyclopts

Cyclopts creates typed command-line interfaces from Python functions and supports subcommands, validators, configuration files, shell completion, dataclasses, complex type hints, and automatically generated help. ([Cyclopts][11])

It could turn SAT scripts into a coherent interface such as:

```powershell
python sat.py run --config baseline.toml
python sat.py sweep --equation-set hsh-v3
python sat.py inspect RUN_UUID
python sat.py render RUN_UUID --projection sigma-t
python sat.py audit RUN_UUID
python sat.py report --since 2026-07-01
```

This is valuable because it separates stable user-facing operations from internal implementation details.

## Requests

Requests is a general HTTP client. It can call APIs, download files, submit data, and manage sessions and authentication.

For SAT, use it when the data source is genuinely dynamic or API-based. For fixed scientific datasets, Pooch’s caching and hashing are generally preferable.

## Tzdata

Tzdata supplies the IANA timezone database for Python environments that do not have suitable system timezone data. It supports reproducible timezone-aware timestamps. It has no direct physics role.

## Narwhals

Narwhals is a compatibility layer allowing code to operate over multiple DataFrame implementations, including pandas, Polars, PyArrow, cuDF, and several lazy backends. ([Narwhals Dev][12])

You probably do not need to call it directly yet. It is useful when writing a reusable library that should accept several DataFrame types. In your present environment it is likely serving another package, particularly a visualization or tabular interface.

It does **not** make Pandas calculations faster by itself.

## Pygments

Pygments supplies syntax highlighting. It supports Rich, documentation systems, code displays, and formatted reports. It has no numerical role.

## Markdown-it-py

Markdown-it-py parses CommonMark-style Markdown and supports configurable syntax and plugins. ([Markdown-it-py][13])

For SAT it could parse report templates or structured notes, but it should not be used to parse the actual mathematical object grammar unless that grammar is deliberately defined as a Markdown extension.

# What the stack can support right now

A defensible current architecture is:

```text
1. H(s)H STATE
   NumPy arrays
   H(λ), frames, phases, invariants, metric, derived fields

2. NUMERICAL OPERATIONS
   NumPy
   differentiation, contractions, decomposition, transforms, checks

3. RUN PROVENANCE
   Pandas + UUID + datetime + hashes
   summaries, comparisons, failure catalogues

4. READOUT / PROJECTION
   explicit SAT code
   RΣ : 4D history → observable 3D/2D representation

5. INTERACTIVE GEOMETRY
   PyVista + VTK
   tubes, glyphs, slices, fields, animations, picking

6. GEOMETRY AUDIT
   Trimesh
   topology of rendered surfaces, watertightness, repair, proximity

7. QUANTITATIVE DIAGNOSTICS
   Matplotlib
   convergence, invariant traces, spectra, residuals

8. INTERACTIVE REPORTING
   Plotly
   run dashboards and shareable HTML

9. EXECUTION INTERFACE
   Cyclopts + Rich
   typed commands, progress, structured failures, status output

10. DATA ACQUISITION
    Pooch / Requests
    pinned datasets or dynamic external inputs
```

That is already enough to build a disciplined **H(s)H numerical workbench**.

# What is actually missing

The phrase “heavy mathematical physics libraries” is too vague. The missing capabilities fall into distinct categories.

## 1. Numerical integration and optimization: SciPy

SciPy would add robust ODE integration, optimization, root finding, interpolation, signal processing, sparse matrices, spatial algorithms, and broader numerical linear algebra. It is the most obvious next foundation library. SciPy defines itself as general open-source software for mathematics, science, and engineering. ([SciPy Documentation][14])

For SAT, this means:

* `solve_ivp` for initial-value evolution;
* boundary-value solvers;
* constrained and unconstrained minimization;
* root solving for closure conditions;
* sparse systems;
* interpolation and splines;
* KD trees and spatial searches;
* signal processing for periodic and superhelical structure.

## 2. Symbolic derivation: SymPy

SymPy adds symbolic calculus, equation solving, matrices, tensors, differential geometry, ODE/PDE manipulation, mechanics, Lagrange’s method, code generation, units, and expression simplification. ([SymPy Docs][15])

For SAT, it could:

* express the master action symbolically;
* differentiate candidate Lagrangians;
* derive Euler–Lagrange equations;
* simplify tensor contractions;
* check dimensional expressions;
* generate numerical NumPy functions from symbolic expressions;
* compare independently written forms for algebraic equivalence.

SymPy should be a derivation and checking layer, not necessarily the high-performance runtime.

## 3. Variational optimization and automatic derivatives: CasADi

CasADi supports symbolic computational graphs, algorithmic differentiation, nonlinear programming, ODE/DAE integration, sensitivity analysis, and optimal control. ([CasADi][16])

This is the most directly relevant addition for the proposed “populate a Lagrangian and let the solver propagate the geometry” direction.

It could encode:

[
S[H]
====

\int L(H,H',H'',\ldots),d\lambda
]

and efficiently generate gradients or Jacobians with respect to thousands of discretized variables.

It does not determine the correct physical action. It solves the action or optimization problem that you provide.

## 4. Labeled multidimensional scientific data: Xarray

Pandas labels rows and columns; NumPy efficiently stores multidimensional arrays. Xarray combines labeled dimensions and coordinates with NumPy-like arrays.

For example, an H(s)H field could carry named dimensions:

```text
run
history
lambda
component
frame_axis
scale
```

rather than relying on undocumented integer-axis conventions. This becomes valuable when SAT states acquire several simultaneous scales, projections, or field components.

# Recommended installation order

The smallest high-value expansion would be:

```powershell
python -m pip install scipy sympy
```

Then, when the action-based solver work begins:

```powershell
python -m pip install casadi
```

Xarray becomes worthwhile when the multidimensional state layout starts becoming difficult to describe with comments and shape conventions alone:

```powershell
python -m pip install xarray
```

I would **not** install a large finite-element, machine-learning, or manifold package merely to make the environment appear more advanced. The next additions should correspond to a specific missing operation:

```text
Need reliable integration/optimization → SciPy
Need symbolic derivation             → SymPy
Need action variation/optimal control → CasADi
Need labeled N-dimensional state      → Xarray
Need formal verification              → Lean, separately
```

One final operational distinction: cloning `invariants_py` does not install it. Until you run an installation command such as `python -m pip install -e .` inside that repository—or deliberately add it to the import path—it contributes no capabilities to the active Python environment. If it is installed from source, its declared dependencies include both SciPy and CasADi, so the resulting environment inventory should be checked again afterward.
