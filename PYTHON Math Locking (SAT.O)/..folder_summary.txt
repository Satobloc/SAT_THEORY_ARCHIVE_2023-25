## High-level role

This folder preserves the SAT.O “structure-locking” layer. In this context, code locking does not primarily mean proof or verification. It means freezing a module's core mathematical definitions into executable symbolic Python structures, usually with SymPy, before downstream derivations rely on them.

Corrected definition:

    Code locking / structure locking = turning a SAT.O module's conceptual and mathematical primitives into fixed executable symbolic objects so later derivations cannot silently drift.

## Process interpretation

The intended SAT.O process appears to be:

    module prose
    -> symbolic structure-lock code
    -> derivation files
    -> audit / verification / protocol checks
    -> synthesis paper

The structure-lock step is important because it stabilizes definitions before an LLM or assistant begins deriving from them. It is an anti-drift mechanism, not a proof of truth.

## Relation to SAT.O

This folder helps explain why SAT.O was the high watermark for process discipline. It attempted to create a reader-verifiable, executable trail from SAT concepts to formal derivations. Even where the derivations are later superseded or judged bridge-like, the process architecture remains historically important.
